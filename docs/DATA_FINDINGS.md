## Decisions taken

The open questions were settled while building the pipeline (`preprocessing/`). Output and before/after numbers are in
`data/processed/profile_before_after.md` (regenerated by every run).

- **Row count.** All 600 fact rows are kept (the guide says 500; the guide rule is "all data in the fact table should be
  considered"). Worth confirming with the teacher. The number 600 is hard-coded as an expectation in a few places, so a
  different answer (for example 500 rows) is a known, small change in exactly these places:
  - `preprocessing/src/fdw/validate.py`: `validate_fact(..., expected_rows=600)` and `assert_valid(..., expected_rows=600)`
    (rule `row_count_preserved`);
  - `sql/99_checks.sql`, check 1 (`fact rows = 600`, `SUM(SegmentCount) = 600`);
  - tests: `test_warehouse.py::test_load_is_idempotent`, `test_pipeline.py::test_row_count_600` and
    `test_stopover_cells_are_empty_not_nan`, `test_assign.py::test_rate_ian_passenger_unchanged`,
    `test_dates.py`, `test_airlines.py`, `test_load.py` (raw row counts) and `test_validate.py::test_default_expected_rows_is_600`.
  Dropping rows would also need a rule for which rows go (not implemented).
- **Routes.** The ticket table has no airports, so the route is fixed per flight number: every ticket group of one `FlightNo`
  gets the same departure, landing and optional stopover airport. Only airports that exist in the airport dimension **and have an
  `airportCode`** are used (as departure, landing or transit), so no report shows an airport without a code. Stopovers are only
  given to routes whose direct distance is at least 900 km (`config.MIN_STOPOVER_ROUTE_KM`). The result is 43 distinct departure
  and 46 distinct landing airports (89 airports used in all, 0 without a code), 95 of 600 rows (15.8%) with a stopover on 14 of
  the 77 flight numbers, 13 distinct transit airports. The shortest stopover route is 1,096 km direct; stopover rows average
  1,943 km against 1,617 km for direct rows.
- **Airlines.** The 7 airlines in the source are extended to 11 by adding 240 supplemental tickets (`IsSupplemented = 1`,
  flight numbers 3U/SC/ZH/9C 9001..9003) and moving four fact ticket groups onto them. The original 568,917 ticket rows are untouched.
- **Passenger keys.** 9 fact `PassengerID`s are missing from the passenger dimension (a defect in the source: 8871, 11387, 11899,
  24773, 28393, 36842, 44143, 52821, 58935). Those rows were remapped to existing passengers not otherwise used in the fact
  (seeded, no dimension rows invented). The old -> new list is in the profile file.
- **Rate and price.** `Rate` is kept as given and only rounded to 2 decimals in the CSV. `Price` = full fare x `Rate`, rounded
  to 10, with full fare = anchor[class] x (`mileage` / 1178) ^ 0.25. The anchors are the source's per-class median of
  `Price / Rate` at its constant 1178 km (Y 1,489, C 5,556); the source has no first class, so F = 1.15 x C (6,389). The
  exponent 0.25 makes the fare grow with distance but taper (a 3,600 km flight costs about 1.3 times a 1,178 km one), so
  F > C > Y at every distance and price rises with distance for a fixed class and `Rate`. Prices now run from 380 to 8,490
  (average Y 1,240, C 4,617, F 5,630) across 28 of the 30 price bands. A price above the top band would be clipped to 8,990
  (the top band's maximum minus 10) as a safety net, but **no row is clipped** (F 0 of 48, C 0 of 132, Y 0 of 420; the
  profile file reports this per class). The constants are in `fdw/config.py` (`FARE_REF_KM`, `FARE_DISTANCE_ALPHA`, `F_OVER_C`).
- **Mileage and dates.** `mileage` is the haversine distance in km including the stopover leg. Dates are recomputed for whole
  ticket groups across Jan to Aug 2021 (8 months, 111 distinct dates); 2021-02-11 to 2021-02-17 is flagged as the spring festival.
- **Stopovers.** Stopover landing/takeoff times are not modelled (hard rule). The transit key stays empty in the cleaned fact file;
  the warehouse maps it to a `No stopover` airport row (`AirportKey 0`).
- **Airport codes.** 47 of the 184 airports have a blank `airportCode` in the source; the code column is nullable in the warehouse.
- **Planes and cabins.** One plane per flight number, chosen by route length: wide-body (`SeatNum` >= 250) for routes of
  1500 km or more, narrow for routes under 800 km, any in between (18 distinct planes used). Cabin classes are mixed exactly
  Y 70% / C 22% / F 8% (420 / 132 / 48 rows). First and business class are only given to rows whose plane has at least 100 seats;
  the 86 rows on small planes (50 to 90 seats) are all economy. A seat of that class is drawn from `DW_Dim_Seat` with a seat row
  that fits the plane (row <= seats / 4), so `PlaneID` and `CabinID` are never blank and vary (467 distinct cabins).
- **Plane size class.** `dw.DimPlane.SizeClass` is derived from the seat count (Wide >= 250 seats, Narrow 100 to 249,
  Small < 100), not from the size label in the source's `planeModel` (大/中/小): for example the 767, labelled 大 (large),
  has 220 seats and is `Narrow`.

## Known artefacts

Things a reader of the cube results should know; none of them breaks a guide #2 rule.

- **Ticket times do not scale with distance.** Departure and arrival times come from the source tickets, which were all
  PEK-SHA flights, so a 3,600 km route has the same flight duration as a 400 km one. Do not analyse duration against distance.
- **Passenger names.** `PassengerName` has NULLs and duplicates in the source passenger dimension, so analyses must group by
  `PassengerKey`, never by name.
- **'No stopover' in the transit role.** Direct flights point their transit key at the `No stopover` member (`AirportKey 0`,
  Province `N/A`). Any transit-hub MDX (for example "busiest transit airports") must exclude that member, or it dominates.
- **SQL Server edition.** The instance used here is SQL Server Express, which has no Analysis Services (SSAS) or Integration
  Services (SSIS). Install the Developer edition (free) before the cube phase.
- **`--raw-dir` and the cache.** `python -m fdw.cli --raw-dir ...` only matters on the first run: the loader reads the CSV cache in
  `data/raw` (`config.CACHE_DIR`) when it exists and ignores `--raw-dir`. Delete `data/raw` to force a re-read of other raw files.
